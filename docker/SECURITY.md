# Security model — Pyongyang Racer play server

This document describes what is exposed, what is protected, and recommended hardening.

## What players connect to

| Layer | Exposed? | Notes |
|-------|----------|-------|
| **Cloud VM (host)** | No (via game URL) | Only HTTP/HTTPS are public. SSH (22) is separate and key-only. |
| **Queue gateway** | Yes, through Caddy | Issues anonymous queue identities and admits one active player. |
| **Selkies container** | No | Streams the isolated X display and PulseAudio monitor only to the gateway. |
| **Full VM desktop** | No | There is no window manager or terminal in the game container. |

Closing Flash shows a black screen until supervisor restarts it. Players cannot
browse the host filesystem or launch a shell through the stream.

## Authentication and admission control

- Visitors do not receive an HTTP Basic Auth challenge. The gateway injects
  Selkies' Basic Auth header on internal HTTP and WebSocket proxy requests.
- The generated upstream password remains in `docker/.stream-password` and
  `docker/.env`; it is never embedded in public HTML, JavaScript, cookies, or URLs.
- Selkies port 6080 and gateway port 8080 are only exposed to the internal
  Docker network. Caddy alone publishes ports 80/443 and terminates HTTPS.
- Queue identities are 256-bit random, `HttpOnly`, `Secure`, `SameSite=Lax`
  cookies. Queue state is held in gateway memory and disappears on restart.
- One identity is active for at most 15 minutes. A shell heartbeat keeps the
  turn alive; 60 seconds without one releases it. Waiting entries expire after
  five minutes without polling.
- The defaults allow 50 waiting entries, one active/waiting entry per client
  IP, and 120 queue-control requests per IP per minute. These values are
  configurable in `.env`.

### Residual risks

| Risk | Severity | Mitigation |
|------|----------|------------|
| Weak/leaked upstream password | High | Auto-generated password stays on the server; rotate it after disclosure |
| Shared session interference | Medium | Only the active random identity may proxy stream HTTP or WebSockets |
| Gateway restart | Medium | Queue is intentionally in-memory; users must rejoin after restart |
| Proxy/IP misconfiguration | Medium | Caddy overwrites `X-Forwarded-For`; never publish gateway port 8080 |
| In-process denial of service | Medium | Capacity, one-entry-per-IP, expiry and basic limits; use an edge/WAF for hostile traffic |
| Old Flash runtime in container | Medium | Non-root container, no host mounts, and only the bundled SWF is launched |
| Docker escape → host | Low | Standard container isolation; keep Docker updated on the VM |

## Container hardening (docker-compose.yml)

- `cap_drop: ALL` — no Linux capabilities
- `no-new-privileges:true` — blocks privilege escalation
- Selkies uses the unprivileged `racer` user
- Gateway uses the unprivileged Node `node` user and a read-only filesystem
- No shell, terminal, or window manager runs on the captured display
- Selkies captures only the isolated 760×500 game display
- Game files are baked into the image; Flash config writes go to `/tmp` only

## Game fidelity

The server runs the **same files** as the Mac app:

- `PY Racer_0509/PYracer.swf` (unchanged SWF)
- Same `.dat` / `.txt` / `.mp3` assets
- Adobe Flash Player **standalone** (Linux build of the same SA family as Mac)

Controls, physics, and animations are entirely inside the original SWF — nothing in this stack modifies game logic.

## Performance limits (not security)

Micro VMs are too small for reliable Flash plus H.264 and Opus encoding. See
`docker/PERFORMANCE.md`.

## Recommended production checklist

1. [ ] Public firewall exposes only TCP 80/443; SSH is key-only
2. [ ] Use a strong internal `STREAM_PASSWORD` (auto-generated by `./oracle/deploy.sh`)
3. [ ] Keep VM and Docker updated: `sudo apt-get update && sudo apt-get upgrade`
4. [ ] Do not commit `docker/.stream-password` or `docker/.env`
5. [ ] Rotate leaked credentials: `STREAM_PASSWORD='new-secret' ./oracle/deploy.sh`
6. [ ] Confirm only Caddy publishes host ports (`docker compose ps`)
7. [ ] Confirm you have the necessary Adobe runtime redistribution rights

## What we cannot guarantee

- **Adobe Flash Player on Linux** is unmaintained and may crash (supervisor auto-restarts it).
- **Segfaults** in Flash are upstream binary bugs — we cannot patch them; we isolate them inside the container.
- **100% uptime** is not guaranteed by the hosting provider.
